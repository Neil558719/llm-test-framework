# 应用范围授权与可信归属

A04b 在 A04a 的登录、角色、Cookie CSRF 和可信 actor 之上，增加 production 的应用范围隔离。subject 来自既有认证链；服务器授予它可访问的 application，客户端的筛选条件、角色名称、请求体或自报 subject 都不能授予权限。admin 同样需要明确的应用授权，可显式授予多个应用。

## 服务器配置

在运行 telemetry FastAPI 工厂的进程中配置以下非凭据设置；受信任的部署人员维护映射，不能让业务请求写入它们。以下身份和应用均为演示占位符：

```powershell
$env:QE_APPLICATION_ACCESS = '{"operator-a":["service-desk"],"operator-b":["other-agent"],"release-admin":["service-desk","other-agent"]}'
$env:QE_TELEMETRY_ALLOWED_APPLICATIONS = '["service-desk"]'
```

`QE_APPLICATION_ACCESS` 必须是 JSON 对象，值为应用字符串数组；`QE_TELEMETRY_ALLOWED_APPLICATIONS` 必须是 JSON 数组，它限制既有机器 ingest token 的所有写通道。空配置/空列表不授予权限；缺少机器配置不会从人类映射继承。拒绝字符串代替数组、空/非字符串/首尾空白/控制字符标识、重复 JSON key 和 `*`。没有通配符或 admin 隐式跨应用授权。

也可由可信服务器启动代码注入 `ApplicationAccessPolicy(mapping)`，通过 `create_telemetry_app(..., access_policy=policy)` 使用；显式注入优先于环境映射。机器范围由 `TelemetrySettings(..., allowed_applications=frozenset({...}))` 注入，或从其 `from_environment()` 加载。配置在应用创建时读取，修改后需重建应用进程。本项目现有 Compose 部署的是 Reference Agent；若另行部署 telemetry API，须向那个服务进程传递这些配置，不能只修改宿主机环境而假定容器已接收。

生产缺少映射默认拒绝人类业务访问，缺少机器范围默认拒绝机器写入。health 与 auth 协议入口保持公开；metrics 为全局技术指标，保留 admin 规则。Reference Agent 的 profile 是全局配置元数据，继续使用 A04a 的读取保护，本轮没有建立 Agent 租户模型。

## 请求和对象边界

| 情况 | production 结果 |
| --- | --- |
| 未登录业务读取/人类写入 | 401 |
| 已认证但没有所需角色、没有应用授权、显式筛选未授权 application | 403 |
| 外应用或不存在的 Trace、反馈/审核/晋级关联 ID、run、发布证据 | 404 |
| 两个都已授权的应用之间建立 Link 或 baseline/candidate 关系 | 400 |
| 用已有 Trace ID 更换 owner，即使机器同时获授两个应用 | 400；若原 owner 未授权则 404 |
| 反馈/审核中伪造 actor 或添加 owner 字段 | 400；认证、角色、CSRF 与对象授权先执行 |

反馈、审核、晋级的归属从真实 Trace 推导；run 的归属来自其持久化报告，既有 run ID 不能被改写到另一个应用。新对象可声明应用，但必须属于服务器授予的范围；声明本身不增加权限。过期 ID 也不能被重用来换 owner。机器 token 不能用于业务读取或人类反馈。

Trace/反馈/审核列表在 SQL 中按允许应用过滤后再 LIMIT/OFFSET；查询原有必需过滤条件和最大页大小保持。趋势的线上计数、反馈数、低质量数、run 数、Token/成本，以及返回的关联链都先在查询层限定范围再聚合。显式 application 趋势还会同步限定其 links，避免在同一响应混入其他已授权应用。没有独立的总数端点或 run 详情 GET；相关数据通过现有趋势/links/发布验证入口读取。

## 发布证据与旧数据

production 创建 validation 时，baseline/candidate 必须同应用，关联计算也仅采用同应用链路。服务端完成计算后写入 `scope_application` 和 `scope_policy_version=1`，并随既有 JSON 保存；HTTP 请求不能自报这两个字段。读取时同时核对创建时证明、真实 run 归属和当前身份权限。缺少/未知证明、缺失/过期 run 或归属不一致统一 404；admin 不能绕过。

旧 validation 即使当前 links 看起来都属于同应用，也不能证明创建时没有使用跨应用数据。旧无证明记录在 production 默认不可读、不能当发布证据；development 可保留原读取。需要可信生产证据时，通过当前 production gate 创建新的 validation ID，不重算或覆盖旧结论。旧跨应用 Link 保持原记录，在生产关联查询、趋势返回和门禁计算中排除。没有归属的旧 Trace/run 不会自动认领、赋予默认应用或批量修改；需在独立审计迁移中确认归属后再处理。

显式 development 模式维持原本地行为，包括调用方自选 actor 和原机器 token 流程。底层仓储/CLI 属于受信任的本地管理接口，新增范围参数默认为 None 以兼容；None 表示未限定，空集合表示零授权。原 CLI 的无范围 validation 没有生产 scope 证明，不能直接变成可信生产证据。

## 兼容和回滚

数据库表/schema 不变；新增字段为 JSON 可选字段，None 时省略，旧 JSON 仍按原形状读取。本轮暂保持 dev3，由主流程整合为下一迁移版本。旧程序的严格 JSON hydration 可能不接受带新字段的 validation；回退必须使用配套数据库快照或验证过的兼容读取器，不能把删证明字段、开放 production 或改成 development 当回滚方案。本轮未部署或更改真实数据库。

本地验证、独立审查、CI、合并、发行与部署分开记录，详见 [A04b 证据](evidence/A04b/summary.md)。真实身份提供方、真实供应商和生产环境验收仍待对应条件。
